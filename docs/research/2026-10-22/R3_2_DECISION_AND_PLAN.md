# Pythia R3.2 — архитектурное решение и план

**Дата:** 2026-10-22. **Архитектор:** Muse (по решению владельца от 22.10.2026).
**База:** принятый baseline `cc118d807c38c4ec76204276616ee7d3c74ada7b` (весь R3.1), ветка `codex/evidence-r32-articles`, checkout `/home/pythia/pythia-evidence-r32`.
**Формулировка карты:** «Контролируемое получение и архивирование связанных official articles. После ревью R3.1 отдельное решение об archive identity/lineage/доступности по времени и подключении article extraction».

## 1. Что такое «связанные official articles» (решение)

Термин в документах проекта нигде не определён (проверено по контракту данных и отчётам R3). Единственное существующее понятие связанной статьи: элементы принятых RSS-лент ФРС несут `referenced_article_url` со статусом `referenced_not_fetched` (`evidence_extract.py`). **Решение:** связанные статьи R3.2 — официальные документы, на которые ссылаются элементы принятых лент (для пилота — monetary RSS), на официальном домене эмитента. Приёмный прогон R3.2 — две статьи-заявления FOMC, чья lineage к фактам ленты `live-r2-revision3` уже установлена в R3.1; путь кода при этом общий для любой allowlisted статьи ленты.

## 2. Archive identity (решение)

- Принятый архив R2 трогать нельзя: его ворота (`validate_capture_result`) пропускают только 8 канонических источников с точными URL, и это инвариант приёмки R2.
- **Решение:** отдельный экземпляр архива для статей (та же машина `EvidenceArchive`, CAS + receipts/revisions, append-only) в новом state dir; реестр источников архива — явный allowlist статей (source_id → canonical article URL), передаваемый в архив параметром. Валидация по умолчанию не меняется: `EvidenceArchive(state_dir)` без реестра работает ровно как раньше (канонические 8), что сохраняется всеми существующими тестами.
- Идентичность документа в архиве статей — та же пара (source_id, initial_url) + цепочка ревизий `prev_revision_id`: повторное получение изменившейся статьи честно даёт новую ревизию, неизменной — идемпотентный replay.

## 3. Lineage (решение)

Архивная схема поля lineage не имеет, и менять её не будем. Lineage статьи записывается в двух местах, как и в R3.1: (1) аудит получения (кто, когда, по чьей ссылке: parent archive/receipt/fact/locator); (2) манифест извлечения (`parent_feed_reference` той же формы, что приняла R3.1) и собранный бандл досье, который дополнительно ссылается на receipt_id/revision_id архива статей. Связь «факт ленты → статья → ревизия архива → досье» таким образом полная и проверяемая по хэшам.

## 4. Доступность по времени (решение)

Receipts фиксируют время каждой попытки и её исход; ревизии — моменты первого наблюдения каждого варианта тела (`first_seen_at`/`first_seen_seq`), `as_of_seq` читателя даёт срез «что было известно на момент N». Для R3.2 достаточно: одно получение на статью в приёмном прогоне + повторное получение тех же статей в тестах жизненного цикла (ревизия при изменении, replay при тождестве) на локальном сервере. Регулярный мониторинг доступности — не R3.2 (это эксплуатация, R8).

## 5. Подключение извлечения (решение)

- Транспорт получения — дисциплины принятого драйвера R3.1.9 (супервизор процесса с жёстким дедлайном, доказанный конец сжатого потока включая multi-member, лимит 2 MiB, изоляция кук, честный аудит, fail-closed публикация), поднятые в продуктовый модуль `python/evaluation/article_acquisition.py`: захват возвращает `CaptureResult` (`complete=True` только при доказанном EOF), далее `EvidenceArchive.record_capture` с явным `probe_result` транспортного уровня.
- Извлечение: из архива (blob по receipt) строится манифест формы R3.1 и вызывается принятый `extract_fed_statement`; бандл собирается принятым `build_fed_statement_bundle`. Профиль — только FOMC statement; иные типы статей архивируются, но извлечение честно фиксирует typed rejection принятого парсера (обобщённое извлечение статей — территория корпуса R4, не R3.2).

## 6. Критерии приёмки R3.2

1. Все прежние тесты зелёны без изменения их смысла (256 evaluation + архивные): поведение по умолчанию архива не изменилось.
2. Новые тесты: реестр статей (приём allowlisted, отказ чужих URL/source_id), жизненный цикл ревизий A→B→A, герметичный захват (EOF/multi-member/лимит/куки/kill), сквозной офлайн путь «локальная статья → архив → извлечение → бандл с валидными proofs и архивной lineage».
3. Один bounded live-прогон: две статьи FOMC получены в архив статей на amper, извлечены оттуда, proofs 21/21, целостность архива и replay проверены; принятые архивы R2 (32 блоба) не изменились.
4. Отчёт, коммит в ветке `codex/evidence-r32-articles`, приёмка с новым baseline в журнале карты. Production/main/paper/Telegram не трогаются; `usable_for_forecast=false`.
