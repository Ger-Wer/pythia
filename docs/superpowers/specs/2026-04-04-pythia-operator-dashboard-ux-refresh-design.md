# Pythia Operator Dashboard UX Refresh Design

Дата: 2026-04-04

## 1. Контекст

Первая версия dashboard уже решила базовую инфраструктурную задачу:

- dashboard опубликован наружу;
- есть app-auth;
- оператор может открыть обзор, прогон, рынок, watchlist и actions;
- визуальная стилистика уже задаёт правильное настроение продукта.

Но первая версия пока не решает главную UX-задачу:

- оператору всё ещё приходится держать модель системы в голове;
- интерфейс показывает поля, но не всегда объясняет смысл;
- некоторые сценарии всё ещё опираются на технические сущности вроде `market_id`;
- operator actions местами выглядят как thin wrapper над shell output;
- dashboard пока не доводит человека до ответа на вопрос: "что произошло и что мне делать дальше?"

Нужна не новая архитектура, а UX-пересборка поверх уже существующего каркаса.

## 2. Цель

Сделать dashboard основным рабочим местом оператора, где человек:

- за 10-30 секунд понимает текущее состояние `Pythia`;
- видит 3-5 главных сигналов без переходов по нескольким экранам;
- может открыть важный рынок без знания `market_id`;
- может добавить рынок в watchlist из любого релевантного места;
- может запускать безопасные действия без чтения сырых логов;
- может понять смысл каждого сложного блока через встроенные подсказки.

## 3. Не-цели

Эта UX-переработка не должна:

- менять forecasting pipeline;
- менять модель безопасности dashboard;
- добавлять shell, Docker-admin или конфигурационный control plane;
- вводить многопользовательский режим;
- превращаться в полный редизайн backend-архитектуры;
- затягивать релиз из-за декоративных UI-улучшений без UX-пользы.

## 4. Главный продуктовый принцип

Dashboard должен строиться вокруг вопроса:

"Что происходит сейчас, почему это важно и что делать дальше?"

Это означает:

- summary-first, details-on-demand;
- действия рядом с контекстом;
- human labels вместо внутренних терминов там, где это возможно;
- минимум технических идентификаторов в основном UX;
- блоки объясняют себя сами.

## 5. UX-принципы v2

### 5.1. Decision-first

Каждый экран должен отвечать на конкретное операторское решение.

- `Overview` отвечает: "система здорова? что требует внимания?"
- `Latest Run` отвечает: "какие сигналы из последнего прогона важнее всего?"
- `Market Detail` отвечает: "почему Pythia расходится с рынком и на что смотреть дальше?"
- `Watchlist` отвечает: "что я отслеживаю и что изменилось?"
- `Operations` отвечает: "какое безопасное действие я запускаю и чем оно закончилось?"

### 5.2. Human-first labels

Видимые подписи должны быть понятны без внутреннего знания системы.

Допустимо сохранить термины `Research+R1`, `Naked R1`, `Watchlist`, `Edge`, но рядом должен быть один из механизмов пояснения:

- явный подзаголовок;
- краткий helper text;
- hover/tap tooltip.

### 5.3. No raw logs by default

По умолчанию оператор видит не `stdout/stderr`, а человеко-понятный результат.

Сырые логи допускаются только как вторичный раскрываемый уровень:

- `Показать технический лог`
- `Подробнее`
- `Открыть лог`

### 5.4. No memory tax

Оператор не должен помнить:

- `market_id`;
- команды;
- внутренние названия backend-сущностей;
- где именно спрятано следующее действие.

## 6. Информационная архитектура v2

Основная навигация переименовывается в более человеческую:

- `Сводка`
- `Сигналы`
- `Избранное`
- `Действия`

Техническое имя `Watchlist` может остаться только как вторичный ярлык.

## 7. Hover / Tap Tooltip System

### 7.1. Назначение

Подсказки нужны не для декоративности, а для снижения когнитивной нагрузки.

Они обязательны для блоков и метрик, где значение неочевидно без контекста.

### 7.2. Паттерн

У каждого сложного блока рядом с заголовком показывается компактная иконка `i`.

Поведение:

- desktop: показать tooltip по hover и focus;
- mobile: показать popover по tap;
- keyboard: tooltip доступен через `Tab` и `Enter/Space`.

### 7.3. Формат текста подсказки

Каждая подсказка имеет одну и ту же микро-структуру:

- `Что это`
- `Почему важно`
- `Как читать`

Подсказка должна быть короткой: 2-4 строки, без длинных абзацев.

### 7.4. Блоки, для которых tooltip обязателен в v2

- `Состояние системы`
- `Research status`
- `Валидные прогнозы`
- `Resolved`
- `Главные сигналы`
- `Edge`
- `Confidence`
- `Base rate`
- `Key risk`
- `Research+R1`
- `Naked R1`
- `Избранное / Watchlist`

### 7.5. Пример

`Edge`

- Что это: разница между оценкой Pythia и рыночной ценой.
- Почему важно: большие расхождения показывают, где модель видит возможную неэффективность.
- Как читать: знак `+` означает, что Pythia оценивает вероятность выше рынка, знак `-` — ниже.

## 8. Экран `Overview` v2

`Overview` становится главным экраном системы.

Он должен состоять из пяти смысловых зон:

### 8.1. Hero summary

Один верхний блок с коротким статусом:

- система `ON / DEGRADED / OFF`;
- research `ON / DEGRADED / OFF`;
- время последнего прогона;
- сколько рынков обработано;
- сколько сигналов требуют внимания сейчас.

### 8.2. Что требует внимания

Отдельный блок:

- 3-5 главных текущих расхождений;
- сортировка по важности;
- короткая причина расхождения;
- CTA: `Открыть разбор`.

### 8.3. Состояние данных

Отдельный блок:

- валидные прогнозы;
- resolved markets;
- watchlist count;
- research degradation warnings;
- если research degraded, это должно быть объяснено человеческим языком.

### 8.4. Быстрые действия

В `Overview` должны быть safe actions:

- `Запустить forecast`
- `Запустить resolve`
- `Обновить статус`

Они нужны именно здесь, потому что `Overview` должен быть рабочей консолью, а не витриной.

### 8.5. Последний результат действий

Небольшой блок:

- какое действие запускалось последним;
- статус;
- краткий итог;
- ссылка `Открыть детали`.

## 9. Экран `Signals` (бывший `Latest Run`) v2

Экран должен показывать не просто таблицу, а рабочий список сигналов.

Минимум:

- сортировка по важности;
- категория;
- рынок;
- `Research+R1`;
- `Naked R1`;
- `Edge`;
- `Confidence`;
- `Research status`;
- кнопка `Следить`;
- кнопка `Открыть разбор`.

Дополнительно:

- quick filters по категории;
- quick filters по силе edge;
- режим `Только сильные сигналы`.

## 10. Экран `Market Detail` v2

Этот экран должен быть перестроен из списка полей в narrative layout.

### 10.1. Верхняя шапка

- headline;
- рыночная цена;
- `Research+R1`;
- `Naked R1`;
- edge;
- confidence;
- кнопка `Следить / Убрать из избранного`.

### 10.2. Главный вывод

Отдельный блок:

- `Вердикт Pythia`
- короткое объяснение, почему оценка отличается от рынка;
- одна фраза "что это значит для оператора".

### 10.3. Почему модель так думает

Отдельные блоки:

- reasoning;
- base rate;
- primary driver;
- confirming signals;
- disconfirming signal;
- key risk.

### 10.4. На что смотреть дальше

Отдельный блок:

- catalyst;
- что изменит оценку вверх;
- что изменит оценку вниз;
- какие сигналы стоит проверять повторно.

### 10.5. Источники и история

- список sources;
- история по дням;
- изменения вероятности по мере накопления прогнозов.

## 11. Экран `Избранное` (Watchlist) v2

Главное требование: без ручного ввода `market_id`.

Поведение:

- рынок добавляется в избранное из `Overview`, `Signals` или `Market Detail`;
- экран `Избранное` только показывает уже отмеченные рынки;
- внутри него можно редактировать заметку и убрать рынок из списка.

Минимальные поля:

- question;
- последняя оценка;
- последнее изменение;
- заметка оператора;
- время последнего обновления;
- кнопка `Открыть разбор`.

## 12. Экран `Действия` (Operations) v2

Этот экран остаётся отдельным, но больше не должен быть лог-консолью.

### 12.1. Карточки действий

Для каждого действия:

- название;
- короткое объяснение, что оно делает;
- риск/ожидание по времени;
- confirm dialog.

### 12.2. Статусы

Статусы должны быть операторскими:

- `queued`
- `running`
- `success`
- `failed`

### 12.3. Результат

После выполнения действия экран показывает:

- что запускалось;
- когда;
- сколько длилось;
- короткий human summary;
- были ли предупреждения;
- CTA: `Открыть технический лог`.

### 12.4. Raw logs

Сырые логи по умолчанию скрыты.

Они доступны только по явному действию:

- `Показать лог`
- `Скопировать лог`

## 13. API и данные, которых не хватает для v2

Для реализации UX v2 dashboard API должен уметь отдавать:

- `resolved_count`;
- `watchlist_count`;
- `top_signals` как отдельную summary-структуру, а не только полный latest run;
- `health`;
- `logs`;
- human-readable action summaries;
- флаг `is_watched` для рынков в списках и деталях;
- историю рынка по дням;
- confirming signals, если они есть в research brief;
- краткий degradation summary для research.

## 14. Контент-стратегия

Почти каждый экран должен отвечать на три вопроса:

- что произошло;
- почему это важно;
- что делать дальше.

Если блок не помогает ответить хотя бы на один из этих вопросов, он лишний или неправильно оформлен.

## 15. Критерий успеха v2

UX-переработка считается успешной, если оператор может:

- открыть `Сводку` и за 10-30 секунд понять состояние системы;
- понять смысл всех ключевых метрик без внешней документации;
- добавить рынок в избранное без знания `market_id`;
- открыть сильный сигнал и понять, почему модель расходится с рынком;
- запустить `forecast/resolve/weekly` и получить human summary без чтения сырого лога;
- пользоваться dashboard как основным рабочим интерфейсом, а Telegram оставить каналом уведомлений.

## 16. Приоритет реализации

Если делать это по уму и без расползания:

1. Пересобрать `Overview` в summary-first экран.
2. Убрать `market_id` из основных пользовательских сценариев.
3. Переделать `Operations` в human-summary-first.
4. Добавить tooltip system и единый паттерн объяснений.
5. Перестроить `Market Detail` в narrative layout.
6. Дотянуть API под недостающие summary-поля.
7. Только потом полировать второстепенные детали.

## 17. Финальная рекомендация

Следующая версия dashboard должна восприниматься не как "веб-интерфейс к API", а как:

- операторская консоль;
- обзорный центр принятия решений;
- безопасное место, где данные, объяснение и действие живут вместе.

Красота уже появилась. Следующий шаг — сделать интерфейс ментально понятным.
