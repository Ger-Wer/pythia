# Pythia Telegram Operator Design

**Дата:** 2026-03-29

**Цель:** сделать Telegram-бота операторским интерфейсом Pythia без веб-дашборда: запускать задачи, читать состояние системы, смотреть последние результаты и вызывать инструкции прямо из личного чата.

## Контекст

Сейчас `Pythia` уже развернута на `amper` в Docker-first конфигурации:

- `pythia-scheduler` выполняет cron-задачи через `supercronic`
- все вычисления и данные живут в `/home/pythia/pythia`
- входящие HTTP-порты не используются
- уведомления в Telegram уже есть, но бот пока не умеет принимать команды

Следующий шаг — добавить отдельный long-running Telegram-сервис, который станет операторской консолью для ручного управления системой.

## Основные требования

Первая версия Telegram-оператора должна:

- работать в отдельном контейнере `pythia-telegram`
- использовать polling через `getUpdates`
- не открывать внешние порты
- принимать команды только от одного пользователя Telegram: `405690972`
- отвечать на русском
- поддерживать английские slash-команды и русские текстовые алиасы
- запускать существующие operational-сценарии, не дублируя бизнес-логику
- не менять `.env` и не редактировать конфигурацию с диска

## Ограничения безопасности

Доступ разрешён только в личном чате оператора.

Правила доступа:

- бот обрабатывает update только если `from.id == 405690972`
- бот игнорирует все сообщения из групп, супергрупп и каналов
- бот игнорирует сообщения от других пользователей
- для неавторизованных пользователей бот не выполняет команду и не раскрывает внутреннее состояние системы

Это даёт минимально необходимый уровень контроля для MVP без усложнения whitelist-группами и multi-user ролями.

## Архитектура

Добавляется второй сервис в `docker-compose.yml`:

- `pythia-scheduler`: как и раньше выполняет cron-задачи
- `pythia-telegram`: постоянно работает в фоне, получает команды из Telegram и запускает существующие сценарии

Новый сервис будет использовать тот же image `pythia:latest`, что и scheduler, но другой `command`.

Это важно по двум причинам:

- один и тот же runtime и один и тот же код используются и для cron, и для ручных запусков
- не появляется отдельный зоопарк образов и зависимостей

## Способ запуска команд

Telegram-бот не должен сам реализовывать прогнозный pipeline, resolution logic или SQL-аналитику.

Вместо этого он вызывает уже существующие operational entrypoints:

- `bash scripts/manual_run.sh forecast`
- `bash scripts/manual_run.sh resolve`
- `bash scripts/manual_run.sh weekly`
- `bash scripts/manual_run.sh edge`
- `bash scripts/day0_check.sh`

Для команд чтения состояния бот использует либо:

- готовые shell entrypoints (`status`, `logs`)
- либо простые read-only SQL-запросы к SQLite
- либо `docker compose ps`

Такой подход сохраняет один источник истины: cron и Telegram используют одни и те же исполняемые пути.

## Формат бота

Файл бота — новый Python-скрипт, например `python/telegram_operator.py`.

Выбор Python, а не TypeScript, здесь предпочтителен:

- в репозитории уже есть Python Telegram tooling
- `requests` уже установлен
- orchestration-команды удобнее и короче реализовать через `subprocess`
- не нужно тянуть дополнительную библиотеку в Bun runtime

Бот будет:

- делать long polling к `getUpdates`
- хранить `offset` только в памяти процесса
- обрабатывать по одному update за раз
- отвечать сообщением в Telegram после каждой команды

Для MVP этого достаточно. После рестарта контейнера бот просто продолжит polling с нового `getUpdates` цикла.

## Набор команд MVP

Slash-команды:

- `/help`
- `/status`
- `/forecast`
- `/resolve`
- `/weekly`
- `/day0`
- `/edge`
- `/logs`
- `/health`
- `/last_predictions`

Русские текстовые алиасы:

- `помощь`
- `статус`
- `прогноз`
- `резолв`
- `недельный отчет`
- `проверка рынка`
- `логи`
- `здоровье`
- `последние`

Допускается, что slash-команды останутся только английскими. Это связано с ограничением Telegram Bot API на формат `BotCommand`. Русские команды реализуются как текстовые алиасы.

## Поведение команд

### `/help` и `помощь`

Показывает:

- список доступных команд
- короткое описание каждой команды на русском
- пояснение, что бот работает только как операторский интерфейс

### `/status` и `статус`

Показывает агрегированный статус:

- состояние docker-сервисов `pythia`
- количество прогнозов в БД
- количество resolved записей
- дату последнего прогноза
- примерную стоимость последнего дня или месяца, если есть

### `/forecast` и `прогноз`

Запускает ручной дневной прогон через существующий operational entrypoint.

Ответ должен содержать:

- подтверждение запуска
- краткий итог после завершения
- число обработанных маркетов или сообщение о том, что подходящих маркетов не найдено

### `/resolve` и `резолв`

Запускает resolution checker.

Ответ должен содержать:

- сколько маркетов было проверено
- сколько разрешилось
- были ли cancelled/N/A

### `/weekly` и `недельный отчет`

Запускает:

- `analyze.py`
- `telegram_bot.py --weekly-report`

Ответ в операторский чат должен подтверждать запуск и завершение.

### `/day0` и `проверка рынка`

Запускает `scripts/day0_check.sh` и возвращает сокращённый вывод:

- сколько binary-маркетов найдено
- сколько в primary и expanded tiers
- verdict (`PASS`, `MARGINAL`, `FAIL`)

### `/edge` и `edge`

Запускает `edge_calculator.py` и возвращает JSON-итог в читаемом виде:

- статус
- `n`
- brier scores
- edge vs market
- решение `GO/PIVOT/STOP`

### `/logs` и `логи`

Показывает последние строки логов `pythia-scheduler` и `pythia-telegram`.

Для MVP достаточно последних `20-40` строк с разумным ограничением длины сообщения.

### `/health` и `здоровье`

Показывает только техническое состояние сервисов:

- `pythia-scheduler`
- `pythia-telegram`
- `healthy / starting / restarting / exited`

### `/last_predictions` и `последние`

Показывает последние несколько прогнозов из SQLite:

- вопрос
- market price
- naked prediction
- research prediction, если есть
- время прогноза

Для MVP достаточно последних `5` записей.

## Русские описания slash-команд

При старте бот должен вызывать `setMyCommands`, чтобы в Telegram отображались команды с русскими описаниями.

Пример:

- `/status` — `Сводный статус системы`
- `/forecast` — `Ручной запуск дневного прогона`
- `/resolve` — `Проверка resolved маркетов`

Это даст русскоязычный UX даже при английских slash-командах.

## Обработка ошибок

Ошибки должны быть мягкими и операторскими по тону.

Примеры:

- если команда недоступна: `Неизвестная команда. Напиши /help`
- если команда запустилась, но subprocess завершился с ошибкой: вернуть краткую ошибку и последние строки stderr
- если Docker/SQLite временно недоступны: сообщить об этом без traceback в пользовательском сообщении
- полный traceback писать только в stdout контейнера

## Анти-конкурентность

Чтобы оператор не запустил две тяжёлые задачи одновременно, бот должен держать простой process-level lock:

- если уже идёт `/forecast`, новый `/forecast` не стартует
- бот отвечает: `Команда уже выполняется: forecast`

Для MVP достаточно in-memory lock в процессе `pythia-telegram`.

Это не абсолютная распределённая блокировка, но в рамках single-container polling-бота этого достаточно.

## Docker-изменения

Нужно обновить `docker-compose.yml`:

- добавить сервис `pythia-telegram`
- использовать тот же image и тот же `.env`
- не публиковать порты
- подключить те же bind mounts `./data:/app/data` и `./logs:/app/logs`
- задать команду для запуска operator bot
- добавить healthcheck на наличие живого polling-процесса

`pythia-scheduler` остаётся без функциональных изменений.

## Что не входит в MVP

Сознательно не делаем в первой версии:

- изменение `.env` и runtime-конфига из Telegram
- изменение фильтров маркетов из Telegram
- multi-user роли
- команды для групповых чатов
- webhook
- inline keyboards и сложные сценарии подтверждений
- историю задач и очередь из нескольких фоновых jobs

Это будет отдельной фазой после стабилизации MVP.

## Критерии готовности

Функция считается готовой, когда:

- `pythia-telegram` работает в отдельном контейнере
- бот принимает команды только от `405690972`
- `/help`, `/status`, `/forecast`, `/resolve`, `/weekly`, `/day0`, `/edge`, `/logs`, `/health`, `/last_predictions` работают
- русские текстовые алиасы работают
- `setMyCommands` показывает русские описания
- scheduler и telegram bot живут одновременно и не мешают друг другу
- документация обновлена на русском

## Решение

Для MVP принимается вариант:

- отдельный контейнер `pythia-telegram`
- polling
- single-user access
- read/run only, без изменения конфига
- английские slash-команды + русские описания + русские текстовые алиасы

Это даёт полноценный операторский интерфейс без веб-дашборда и без лишней сложности в первой итерации.
